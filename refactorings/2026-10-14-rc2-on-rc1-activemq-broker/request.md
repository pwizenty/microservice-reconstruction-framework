## Finding

Security smell: Non-Secured Service-to-Service Communications
(Ponce et al. 2022, §3.7). Root cause 2 of 2 in this system.

An ActiveMQ broker is reached over a plaintext transport by every service that
produces to or consumes from it. This cause accounts for 6 of the system's 9
findings, across 6 queues.

## What is already done in this tree

**Root cause 1 is already resolved here, in the commit this tree is at.** The
Customer Core serves mutual TLS and its three callers present client
certificates. Read that commit before you start: it establishes the
certificate infrastructure, the property conventions and the Docker Compose
arrangement you should extend rather than duplicate.

In particular:

- A development CA, a shared trust store and a per-service key store already
  exist, generated by a committed script. **Extend that script** for any peer
  that now needs material. Do NOT add a second script, a second CA or a second
  trust store.
- `.gitignore` already excludes the generated material. Do not duplicate those
  rules.
- `REFACTORING-NOTES.md` already exists and describes root cause 1. **Append**
  a section for this cause; do not overwrite what is there.
- `docker-compose.yml` already mounts certificates for several services and
  already addresses the Customer Core over https. Extend it.

## The facts, as the reconstructed LEMMA models state them

Six producer channels, on CustomerSelfService and PolicyManagement, all of this
shape:

    @javaWithSpring::_aspects.MessageChannel(role = "producer",
        queue = "newpolicies", target = "RiskManagement", broker = "activemq",
        scheme = "tcp", transport = "plaintext")

The six queues are: insurance-quote-request-event-queue,
customer-decision-event-queue, insurance-quote-response-event-queue,
insurance-quote-expired-event-queue, policy-created-event-queue, newpolicies.

A seventh participant holds no channel aspect of its own because it is not a
Java service: the consumer of `newpolicies` is a Node service. It must be
refactored too, or the system will not run once the broker requires TLS.

The models carry no file paths by design. Locate the code yourself.

## Scope

This cause only: the broker, every Java client of it, and the Node consumer.
Do NOT change anything belonging to root cause 1 - the Customer Core's
connector or its callers' addresses and clients are already correct.

## Done when

- the broker's connectors use a TLS scheme and NO plaintext connector remains
- every client addresses the broker over that TLS scheme and presents a
  client certificate
- every affected Java service still compiles
- the test suite still passes on a clean checkout of your patch, with no
  generated key material present
